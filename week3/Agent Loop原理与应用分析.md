## 一、本节概览
进而讲清 **Agent Loop 为什么存在、每一轮之间如何依赖**，并区分 Function Calling、Tool Runtime、Agent Loop、LoopGuard 四个概念的职责边界。最后给出框架复用建议、三层递进学习目标，以及"什么场景下不需要 Loop"的判断标准。

---

### Agent Loop 极简总结

1. 对比演示：成熟 Agent（Trae）可直接完成代码链路梳理；自研 Agent 需额外提示词，分步探查目录、调用工具、写入结果。
2. 核心：Agent Loop 存在的本质 ——**后续动作依赖上一步新产出信息**；前置信息充足、任务可并行拆分时，不需要 Loop。
3. 四层职责
   - Function Calling：模型决定下一步动作
   - Tool Runtime：校验并执行本次工具动作
   - Agent Loop：拿到工具结果后，更新上下文，驱动下一轮大模型决策
   - LoopGuard：管控最大轮数、重复动作、总时长，决定任务是否终止
4. 执行边界
   - 单次工具调用：Tool Call → Tool Runtime → Tool Result
   - 完整任务：上下文 → LLM 决策 → 工具调用 → 执行 → 结果 → 更新上下文，循环往复
5. 选型：优先复用 Pi 框架（TS/Bun 编写，编码 Agent 底座，封装 Loop、工具调度、LoopGuard）；仅特殊技术栈才自研循环。
6. 学习目标：分清四层概念、接入工具实现循环、校验 Loop 约束。


### 4. 两类 Agent 的差异对比

| 维度 | Trae（成熟 Agent） | 自研 Agent |
|---|---|---|
| 文件读取 | 打开时已扫描全部文件夹 | 需要逐个文件查找、读取 |
| 运行前提 | 可直接跑 | 需先启动网关 |
| 调用工具 | 工具链由框架内置 | 调用的工具与轮数各不相同 |
| 产出结构 | 分层文档 + 引用路径 | 同样输出架构说明 + 引用清单 |

### 三、代码分析的通用流程

不管是 Trae 还是自研 Agent，理解代码的流程是一致的——**不会直接把全文丢进上下文**，而是：

1. 明确用户目标；
2. 查询项目目录结构；
3. 搜索定位相关文件；
4. 读取路由层；
5. 读取 Service 层；
6. 读取认证模块；
7. 最后写入结果文档。

不同 Agent 的差别只在于：调用的工具不同、所需轮数不同。以自研 Agent 为例，一轮典型轨迹是：`list file` 找到文件 → `search_code` 搜索 → 读取文件 → 写入结果文件。

### 四、Agent Loop 的核心逻辑

### 1. 多轮轨迹之间的依赖关系

在整个约八轮的轨迹里，一个关键事实是：**每一轮要往下执行，都必须依赖上一轮返回的真实结果**。用生产者—消费者的逻辑理解，每一步的上一步就是它的输入来源；缺少任何一轮，后续都走不下去。

典型的逐级发现过程：

- 第二轮时模型并不知道所谓"登录文件"在哪里；
- 读到对应 Service 后，才知道密码相关逻辑在 Service 文件里；
- 继续往下找，才定位到 `email`；
- 再找到 user 表时，才知道用户名到底存放在哪里。

也就是说，必须读完上面这些证据，才能推出下一步该做什么。

### 2. 为什么复杂任务需要 Loop

> **复杂任务需要 Loop，不是因为步骤多，而是因为下一步要依赖上一步新产生的事实；基于这个事实，再驱动下一步继续往下执行。**


### 3. Loop 的结束不由 Loop 自身决定

任务干到什么程度结束，并不是由 Loop 决定，而由下一讲涉及的 **Planner（规划器）** 判定。


#### 三层递进学习目标

1. **能解释清楚**：工具调用（Function Calling）、运行时（Tool Runtime）与 Agent Loop 到底有什么区别；
2. **能动手接入**：把 Python 与工具结果结合起来——以前只处理一轮，现在能接住工具结果继续处理下一轮，一轮一轮做到任务完成；
3. **能验证生效**：验证最大运行轮数、完成条件、重复动作、取消动作等约束确实生效。验证方式：在codebase agent 目录的 README 中找到测试命令运行；本次共跑了 6 个测试，全部通过。

> 三个层次递进：先理解 Loop → 再动手接入 → 最后验证它是否按预期在预算内运行、不跑偏。

本节最终要掌握的三件事：**解释 Loop 为什么存在及其执行顺序；明确 Loop 的审查边界；证明 Loop 在预算之内、不会跑偏。**

### 图 1：四个对象分别回答什么问题


| 对象 | 负责回答的问题 | 示例 |
|---|---|---|
| **Function Calling** | 模型怎样表达下一步动作？ | "调用 `search_code`，搜索 `auth`" |
| **Tool Runtime** | 这一次动作能否执行，怎样执行？ | 校验路径、权限、超时并运行搜索 |
| **Agent Loop** | Tool Result 回来以后怎么办？ | 把命中结果交给模型，继续读取文件 |
| **LoopGuard** | 整个 Run 还能不能继续？ | 最大轮数、重复动作、总时间 |

逐层职责解读：

- **Function Calling**：推测下一步要执行什么动作，是模型对动作的表达；
- **Tool Runtime**：运行时前后的处理——执行前校验权限等，执行后做收尾；
- **Agent Loop**：承接工具执行完之后的结果，校验是否真正拿到了用户问题想要的答案；没命中就回去继续执行；
- **LoopGuard**：判断整个 Run 还能否继续跑下去，依据是最大轮数、重复动作、总执行时间等。

### 图 2：一次工具调用的边界 vs 一个任务的执行边界


**一次工具调用的边界**（第二章已讲过的单轮）：

```text
Tool Call
  → Tool Runtime
  → Tool Result
```

**一个任务的执行边界**（叠加 Loop 之后）：

```text
当前 Context
  → LLM Decision
  → Tool Call
      → Tool Runtime
      → Tool Result
  → 更新 Context
  → 下一轮 LLM Decision
```

- 工具执行一定有结果，结果回来后先更新上下文，再进入下一轮大模型决策；是否还能再跑一轮，由任务情况与工具调用情况决定。
- 整体最多能执行几轮，由 **LoopGuard** 决定。
- Loop 增加的是连续运行能力，但不能绕过之前工具层的校验与权限能力。

#### 八、什么时候不需要 Loop

是否使用 Loop，判断依据是：**下一步所需的事实，是否由上一轮工具结果产生。** 以下场景不需要 Loop：

- **前置原因已经非常充足**：大模型无需继续跑轮；
- **工具只读**：可以并发运行；
- **多件互不相关的事**：无需 Loop；若其中存在读写，还可以拆成多个子 Agent 分别运行，最后再汇总结果。

### pi的loop实现
核心只有4步
- 请求模型
- 执行工具
- 回写工具结果
- 继续发起下一次请求

```
async function runAgentLoop(context, config) {
  while (true) {
    // 1. 基于上下文和配置请求模型（流式响应）
    const assistant = await streamAssistantResponse(context, config);
    context.messages.push(assistant);

    // 异常 / 中止：直接退出循环
    if (["error", "aborted"].includes(assistant.stopReason)) return;

    // 2. 从响应中筛出工具调用
    const calls = assistant.content.filter(x => x.type === "toolCall");
    // 没有工具调用：本轮结束，退出循环
    if (calls.length === 0) return;

    // 3. 执行工具（由 Tool Runtime 完成），结果回写上下文
    const results = await executeToolCalls(calls, config);
    context.messages.push(...results);

    // 4. 业务层中止判断：是否需要再进下一轮
    if (await config.shouldStopAfterTurn?.({ assistant, results })) return;
  }
}
```
#### 解释流式响应
是调用大模型流式接口，一遍收流，一遍拼装，等流全部结束后，返回一个完整归一化后的assitant消息对象
入参
- context:上下文对象，里面context.message是历史对话消息数组（用户，assistant, 工具结果）
- config:配置，包含模型地址，秘钥，工具列表，超时，重试，provider适配器等
assistant对象的结构
```
{
  // 内容块数组，里面区分文本 / toolCall
  content: Array<{ type: "text" | "toolCall", ... }>,
  // 停止原因，对应代码判断：error / aborted / stop / tool_calls
  stopReason: "error" | "aborted" | "stop" | "tool_calls",
  id: string,
  role: "assistant",
  usage?: { input: number, output: number }
}

```
###### 内部做了什么？
1. 拿 `context.messages` 拼成请求体，发给 LLM 流式接口（OpenAI / Anthropic / Ollama 等）
2. 持续消费 stream 分片，把增量文本、增量 tool_call JSON 片段实时拼接
3. 处理各家模型返回格式差异，做归一化（统一成 Pi 的 content-block 结构）
4. 流结束之后，把拼装好的完整 assistant 消息返回，**不是返回流本身，是收集完流之后返回最终消息**

> 
> 注意：这个函数是课程示例里的包装函数，不是 pi 包原生导出函数；pi 原生底层是 `stream()` 返回异步迭代流，示例封装了一层，等流跑完再返回完整消息，方便写这个极简 while 循环演示代码

长任务循环中最容易出错的外围环节：

- **工具执行前**：如何做工具准备；**执行后**：如何收尾；
- **事件响应时机**：在一轮的哪个位置响应事件；
- **副作用处理**：工具调用前后的作用范围与副作用如何管理。

### 四、Turn（一轮）与 Run（一次任务）的层次区分

为了把长任务循环讲清楚，需要先把 **一轮** 与 **一次任务** 分开。

### 1. Turn：一轮
一轮指与模型进行一次完整的对话
1. 与模型对话；
2. 判断是否需要调用工具（工具可以是 0 个或多个）；
3. 工具在运行时执行并返回结果；
4. 这一轮结束。

一轮结束后，结果累积到上下文中，由大模型判断是否开启下一轮。Loop 内循环不关心本轮跑的是什么业务——调什么模型、什么工具、得到什么结果，它完全不管，只关心这一轮能不能跑起来。

### run：一次任务
一次任务（**run**）指从第一轮开始、到最后一轮结束的整个运行过程。统计轮数、记录工具动作、观察模型等操作，都放在每一轮的外层做；对单次 run 执行情况的关注、层次划分与业务抽象，也都在这一层。

### 3. 典型事件序列

一次 run 的典型事件序列如下（图 2）：

![典型事件序列](images/event-sequence.png)

```text
agent_start
  ├─ turn_start
  ├─ message_start / update / end
  ├─ tool_execution_start
  ├─ tool_execution_end
  ├─ Tool Result message_start / end
  ├─ turn_end
  │
  ├─ turn_start
  ├─ message_start / update / end
  ├─ turn_end
  └─ agent_end
```

- 看到"处理整个事件序列"，指从 `agent_start` 到 `agent_end`（一次 run）；
- 看到"处理一次 turn"，指中间某一小轮的结果。

先用它们做三件事：
- 统计轮数；
- 记录每次工具动作；
- 判断本轮结束后是否还允许继续。

## ReAct 与 Plan-and-Execute
### ReAct 是观察 - 决策 - 行动闭环，核心是让推理和行动交替发生，每次行动都依赖最新的信息/事实。
 基本流程
 - Observe:看到当前的机构和已有的工具结果
 - think/decide(决定): 判断缺少什么证据
 - Act:提出一个tool call
-observe 读取call result

ReAct的价值是：每一步都有可追溯的观察依据
loop:决定要不要继续，  ReAct 决定：下一步往哪里走


#### Plan-and-Execute：先定路线
Plan-and-Execute是 先问“目标是什么”再把目标拆成若干个子目标，然后由执行器逐一完成
关注：总目标是什么。应该拆成哪些阶段

#### 二者结合使用

- Plan 负责整体路线；
- ReAct 负责执行过程中的局部决策。

模式	             回答的问题
ReAct	            这一步往哪走
Plan-and-Execute	整体怎么走

loop是执行发动机，plan是任务导航

### 循环中止：模型说完成，能交差吗？
模型停止调用工具，只说明他准备完成，业务是否完成，要看证据

#### 不应该继续调用模型的场景：
- provider返回aborted
- 用户主动取消
- 达到最大轮数或总时间
- 发生不可恢复的权限拒绝
- 相同动作反复出现
- 需要人工确认但暂时无法获得确认

#### 完成契约校验（verifyCompletion）
完成契约：有可检查条件，并返回缺失项
返回缺失项，而不是只返回布尔值，Host 才能把具体缺口作为 Follow-up 交回模型，例如 “尚未生成说明文档，请完成写入”。
```
function verifyCompletion(evidence: Evidence): string[] {
  const missing: string[] = [];

  if (evidence.readFiles.size < 3) {
    missing.push("缺少源码阅读证据");
  }

  if (!evidence.writtenArtifacts.has("artifacts/login-flow.md")) {
    missing.push("尚未生成说明文档");
  }

  return missing;
}

```
但最低门槛不等于完整业务验收。读三个文件不能证明读对了，写入成功也不能证明内容正确。最终仍要检查调用链、引用路径和关键结论是否有源码依据。

##### verifyCompletion 执行时机
在**每一轮 turn 工具执行完毕之后执行**；哪怕本轮模型不再输出 tool_call、主动停掉工具调用，Host 依然要执行一次验收，根据证据判断是真的完成，还是需要 Follow-up 继续补任务。

##### 什么时候不跑 verifyCompletion？

- 触发第四层硬终止：aborted、权限拒绝、运行时崩溃、用户取消，直接终止，跳过验收。
#### 限制： 时间，最大轮次，token，和费用预算
##### 为什么还要最大轮数
因为验收可能一直不通过。模型可能反复改写文档，也可能受工具故障影响，始终拿不到证据。
设置maxturns=xx之后，按turn_start计数，到达上限后不会发出新的模型请求。
到达上线后报告
- 已经完成什么
- 缺少什么
- 为什么停止
- 是否还有可执行建议

### Host Follow-up
> 背景： 是LLM Agent(带工具调用，循环执行)里面的术语，不是前端浏览器的Host

#### Host 
Host = 调度宿主/主控程序
> 就是跑在模型外面，管整个agent循环的代码，是Agent的总指挥，大模型本身只是一个被它调用worker

- 模型只负责思考，输出tool_call,输出文本
- Host负责：调用工具，保存证据，计数轮数。判超时，调用verifyCompletion,判断要不要继续下一轮，停止，返回给用户

Host 内部核心结构
Host（主控）
├─ 状态存储：turn轮数计数器、token消耗、耗时、evidence证据池
├─ 配置：maxTurns最大轮数、最大时长、预算上限
├─ 工具调度器：执行tool call（读文件、写文件等）
├─ 完成校验器：verifyCompletion(evidence) 【第三层判断】
├─ 终止规则判断器：四层终止逻辑 + 各类停止条件（aborted、权限、重复动作等）
└─ 消息组装器：把【缺失项】包装成 Follow-up 消息丢回给大模型

四层终止逻辑为
层级	触发条件	    由谁判断	        结果
第一层	无 Tool Call	pi 框架	           协议停止
第二层	达到最大轮数	Host 配置	         硬限幅触发，强制截断
第三层	完成条件不满足	verifyCompletion()	继续或拒绝
第四层	不可恢复错误	运行时	              硬终止

#### Follow-up 
Follow-up 是什么
> 跟进提示/ 追加任务消息

当 `verifyCompletion` 返回了缺失项（比如：没生成 md 文档、源码读的不够），Host 把这个缺口，包装成一条新的用户侧消息，发给模型继续干活，这条消息就是 Follow-up。

关键规则（原文重点）：
Follow-up 属于同一个目标下的追加任务，**不会重置 Host 的 turn 轮数计数器**，依然占用 maxTurns 配额，防止无限循环。

#### 面试精简版（可以直接背）

- Host：Agent 的主控调度程序，负责管理循环、轮数、工具执行、证据保存、完成校验、终止判断，模型是被 Host 调用的节点。
- Follow-up：校验不通过时，Host 把缺失的验收项包装成跟进提示，发给模型继续补任务；**不重置轮数**。

### Host 是调度外壳，Plan-and-Execute 是 Agent 内部的执行策略
二者不在同一个维度：

- **Host：调度层（外层）**，管循环、轮数、终止、证据、预算、是否继续跑；是 “控制器”
- **Plan-and-Execute：Agent 思考策略（内层）**，模型自己先出计划 plan，再一步步 execute 执行；是 “模型干活的方式”

### Host 干什么（和 Plan&Execute 互不干涉）

Host 根本不关心模型是用 Plan-and-Execute、ReAct、Self-Ask 还是别的思路：

流程：

1. 用户把任务交给 Host，Host 将任务下发给 LLM；LLM 采用 Plan-and-Execute 策略，生成执行计划，输出 tool_call
2. Host 执行工具调用，把工具返回结果存入 evidence 证据池，turn 轮数 +1
3. 本轮工具（turn）执行结束后，Host 执行 `verifyCompletion(evidence)` 做客观验收
   - ✅ 验收通过：正常终止，返回交付成果
   - ❌ 验收不通过：Host 组装 Follow-up 跟进提示追加到对话上下文，进入下一轮循环（**轮数计数器不清零**）
4. Host 持续监控全局限制：轮数、耗时、Token / 费用预算，达到 `maxTurns` 上限直接强制截断，不再发起新的模型请求
5. 运行时捕获异常：Provider 返回 `aborted`、权限拒绝、重复动作、用户主动取消等不可恢复情况，直接硬终止，输出终止原因、已完成项、缺失项

> 
> 不管模型内部是先写计划再执行，还是 ReAct 想到哪做到哪，Host 都用同一套四层终止规则罩住它。

> Plan 里面已经写好了一共几步、什么时候结束，Host 再做一套验收终止，是不是重复、打架？

两个 “结束判断” 是两回事：

1. **模型侧的计划结束（Plan 认为做完了）**：只是模型自己主观判断 “我计划里的步骤跑完了”，对应你原文的「模型停止调用工具」
2. **Host 侧的完成契约校验（verifyCompletion）**：客观检查证据，是**独立于模型的客观验收关卡**

👉 痛点就是你原文举的例子：
模型 Plan 走完了，说 “我完成了”，但它忘了生成 md 文件。
**模型自己的计划判断是不可信的，必须由 Host 独立验收。**
Plan-and-Execute 只负责 “怎么干”，Host 负责 “干没干成、要不要停、防止无限循环”。

Plan-and-Execute 是模型的任务拆解执行思路，属于模型思考策略；Host 是外层独立调度器，不关心模型用什么策略，统一负责轮数、证据收集、完成契约校验、终止控制。模型说自己做完不算，Host 的证据验收才算。

模块	            关注点	                                    谁来做	                核心输出
Plan-and-Execute	任务怎么拆、顺序、动态改计划	                LLM     	          执行计划、tool call
Host	            循环管控、终止、证据验收、预算轮数	            主控代码	            是否继续、Follow-up、终止结论


### 为什么一次 Tool Calling 不够
- **单次 Tool Calling 是最小执行单元**（相当于 “手”，负责把一步动作做对、做可控）
- **Agent Loop 是持续推进机制**（相当于 “脑 + 记忆”，负责根据结果决定下一步，把长任务走完）

### 工具结果怎样驱动下一轮？
工具结果驱动下一轮的本质，是**把工具执行的产出作为新的上下文信息回喂给大模型，让模型基于更新后的全局信息重新推理决策，从而自主产生下一轮动作**，而非由预设流程或人工指令规定下一步做什么
#### 完整的驱动闭环 5步
- 上一轮执行收尾，生成标准化工具结果
  > 系统会对结果进行标准化处理，保证模型能读懂
  - 无论工具执行成功。失败，超时，权限限制，还是返回空结果，都会被包装成统一格式的工具返回消息
  - 对超长结果进行截断，摘要或脱敏处理，避免撑爆上下文窗口
- 上下文注入：把结果追加到对话历史
  > 驱动最总要的一步， 系统会把这条工具返回消息，追加到完整的对话历史中，和【原始目标，历史思考，历史工具调用，历史结果】放在一起，构成全量任务进度上下文
- 模型重推理：基于新信息重新评估任务状态
  > 拿到更新后的上下文后，模型会重新做一次推理，判断3件事
  - 当前离最终目标还差什么？
  - 刚拿到的结果提供了哪些新的线索，有没有推翻之前的判断
  - 下一步最优做什么？才能有效推进任务
- 输出下一轮决策
  - 继续推进：信息不足，生成新的tool call，执行下一个工具动作
  - **修正方向**：结果不符合预期，调整策略重试（比如换搜索关键词、修正文件路径、换排查路径）；
  - **任务完成**：信息已足够，输出最终答案，终止循环。
- 校验与执行，进入下一轮
  > 系统对新的tool call做参数校验，权限校验，审计记录后执行工具，执行完成后在回到第一步，形成闭环  

补充：  
1. **每轮都是全量思考，不是链式接力**：模型每一轮都会回顾完整历史，不是只看上一步结果，因此可以随时纠正之前的偏差，不会一条路走到黑。
2. **驱动必须有停止边界**：循环不能无限进行，工程上会通过最大轮次、完成契约校验、Token / 时间预算来兜底终止

### 模型说完成以后，程序凭什么决定能不能交付？
模型说完成了，只是它主观表述来决定是不是交付。可能有幻觉，漏项，降标就提前收尾  
靠 **[前置约定的验收标准+可追溯的客观证据+独立的校验逻辑]**
verifyCompletion(验证完成)，证据池，完成契约机制，程序判定分为4层
1：前置基准：planning阶段就锁死“完成标准”
  - 每个子目标（planStep）都会写明可验证的完成条件
  - 程序会把这份【子任务+验收标准】结构化存储，作为后续所有校验的唯一基准
    - 例：‘修复会话过期bug'的完成标准=分层测试全部通过，无401复现，报错日志清零

     objective 描述这一步要达成的结果  
     dependsOn:列出前置步骤的ID，控制执行顺序  
     successCriteria：描述这一步的验收标准  

2:事实依据：证据池（evidence）沉淀所有执行痕迹

  - 工具池里面内容是工具真实执行的产物：搜索记录，文件读取，测试日志，代码diff,报错信息等，全程不可篡改。

3: 核心校验verityCompletion独立校验环节
 这是专门负责判断能不能交付的独立逻辑，在模型声称完成时，强制触发，部分实现里每轮loop结束也会预检，  
  - )硬规则校验（程序自动执行）用代码做结构化对比，不依赖模型判断  
    - 子目标完成度：检查所有planstep的状态是否全部标记为done，有没有遗漏必做步骤
    - 证据完整性：每个子目标的验收标准，是否都有对应的证据匹配
    - 产出物合规性：最终交付物格式，内容范围是否符合要求
    - 异常清零：任务过程中报错，失败项是否都已经解决，没有遗留未处理异常  
  - )模型辅助校验

- 子目标逐项完成状态
- 全部证据清单与索引
- 校验通过记录
- 最终产出物

### 文档里面说的 Planning 是 Plan-and-Execute 的 plan 吗？
 **Planning 与 Plan-and-Execute 范式中的 Plan 阶段核心思想同源，但二者并不完全等同**
 - 狭义 Plan-and-Execute：通常在任务启动时就输出完整的全链路计划，执行阶段以 “按计划走” 为主，重规划只是异常场景的兜底。
- 文档的 Planning：初始只输出粗粒度的主干计划，执行过程中可以根据工具返回的结果随时调整 —— 比如搜索到新线索就新增子步骤、发现原路径走不通就废弃分支、验证通过就标记子目标完成。它和 Agent Loop 的每一轮推理深度绑定，走一步、校准一步计划。

### 需要掌握的知识：
#### 单轮Tool Calling的局限
单次动作受控，必须预先明确指令
- 主要表现在，无法覆盖长流程。
- 无法动态反馈调节能力 
- 无任务状态留存，比如遇到中断，人工审批后无法继续

#### 为什么复杂任务需要多步执行
- 多步骤存在强依赖关系，下一步依赖上一步的输出的信息。
- 动态调整执行路径。

#### ReAct模式
ReAct:reasoning-acting 推理和行动交替  是agent loop最基础实现形态  
核心逻辑：边推理，边行动，模型基于当前全部上下文推理判断下一步的动作，在调用对应工具的执行
工具执行完毕后，将新的结果补充进上下文，开启新一轮推理

#### Plan-and-Execute
计划-执行，是比基础ReAct更进阶的长任务模式。
核心逻辑是，做长任务规划，在按计划落地，拿到任务后，先把大目标拆解成多个有先后依赖的，带明确完成标准的子目标
之后按照规划顺序逐个执行子任务。执行过程中可以根据实际结果动态调整路径

#### 最大循环次数
工程叫maxturns 是长程agent的兜底防护机制
- 给单个任务设置一个轮次上限，每完成一次【思考-执行-观察】的完整循环，计数+1
- 当循环次数到达上限后，强制中止任务
- 它能避免死循环，无进展任务的硬限制，保障agent运行的整体可控性

#### 循环终止条件
agent 循环分为【正常终止】，和【兜底、异常终止】两类
- 任务达成：：模型判断所有目标均已完成，，收集到足够信息，可以输出最终结果
- 达到最大循环次数，触发轮次兜底上限，强行终止
- 任务不可行，经过多轮尝试后，确认任务无法完成，主动中止说明原因。比如：目标文件不存在，无操作权限
- 人工干预中断。收到用户中断指令

#### 死循环识别
死循环是长程agent的典型异常，主流识别围绕【无实质性进展】展开
- 重复动作检测：连续多轮参数一致，工具一致，且返回结果没有新增有效信息
- 进度停滞检测：多轮循环后，任务核心目标没有实质性推进，关键问题未取得突破，上下文没有有效新增信息
- 逻辑闭环检测：模型推理路径陷入自循环，比如从A问题推导到B，又从B推导到A。反复绕圈识别到死循环，通常会触发策略调整，强制跳出或上报人工介入

#### 任务中断与恢复
中断场景： 人工审批暂停，程序异常退出，用户主动暂停，工具调用失败
恢复： 核心逻辑是状态持久化
核心状态留存：每一轮循环结束后，持久化存储 进度，

#### 计划与实际执行偏差处理：根据工具结果，测试失败，或上下文变化调整下一步动作
通常按偏差严重程度分三级处理：
1 轻度偏差：局部调整，不修改整体计划
 比如： 单次工具调用失败，参数校验不通过，结果有瑕疵   解决：重试工具，调整参数，更换同类工具
2 中度偏差： 触发局部计划修订
比如：子目标执行未达验收标准，（如单元测试失败），发现计划外的小依赖，工具返回了预期外的关键线索  解决：在原有大框架下，新增/删除后续子步骤，调整子目标顺序，不用推翻整体规划
3 重度偏差：触发全局重规划
比如：原有路径完全走不通，核心前置条件不成立，发现完全改变任务方向的新信息。解决：基于当前全部上下文，重新拆解子目标，生成全新的执行计划
**兜底机制**：若多轮修订后仍无进展，触发最大轮次 / 死循环检测，终止任务并输出当前进展与卡点，交由人工介入。
